# 開発フローと組み合わせた使用例

これは`redmine-tools-for-agents`の利用例の一つです。**本スキル自体は、ここで説明する開発フロー（STEP区切り）
に依存しません**。著者自身の開発環境では、エージェント定義ファイル（例: `CLAUDE.md`）で以下のような
STEP0〜6の開発フローを定義しており、各STEPの区切りで本スキルを次のように使っています。自分の開発
フローに合わせて読み替えてください。

| STEP | 内容 |
| --- | --- |
| STEP0 | 壁打ち・構想整理 |
| STEP1 | 仕様確認（要件定義ドキュメントへの反映） |
| STEP2 | 設計 |
| STEP3 | テストRED |
| STEP4 | 実装 |
| STEP5 | テストGREEN |
| STEP6 | ドキュメント反映 |

## 使用場面（著者の開発フローにおける例）

- **STEP0完了時（分割なし）**: Obsidianでの壁打ちがまとまったら、`create_issue.sh` で要件チケットを
  作成する。チケット作成後、そのチケットIDをSTEP1へ引き継ぐ
- **STEP0完了時（分割あり）**: 壁打ちの結果が複雑で複数チケットに分割すべきとAIが判断した場合は、
  分割案（親チケット1件＋子チケットN件の構成）をユーザーに提示し、承認を得てから登録する。承認後、
  まず親チケットを `create_issue.sh` で作成し、続けて各子チケットを `--parent` に親チケットの
  IDを指定して作成する
- **ユーザーが直接Redmineにチケットを作成した場合**: チケット作成の主体（AIかユーザーか）は問わず、
  以降はチケットIDを起点に同様にSTEPを進める
- **STEP1（新規）**: `get_issue.sh` でチケット内容を確認し、その内容を元に`00-REQUIREMENTS.md`を作成する
- **STEP2以降で仕様変更が発生した場合**: `create_issue.sh` で仕様変更用の要件チケットを作成する
- **STEP1（仕様変更）**: `get_issue.sh` でチケット内容を確認し、その内容を元に
  `0X-REQUIREMENTS-CHANGE-*.md` を作成する
- **チケット参照によるSTEP1着手**: 「#123 の要件を確認して実装に着手」のようなチャットを検知した
  場合、まず `get_issue_recursive.sh` でチケット内容（添付画像・関連チケット・本文中のリンクを含む）
  を取得する。検出された外部URLがあれば、WebFetchツールで内容を取得したうえで判断材料に加える。
  その後、著者の環境では、CLAUDE.mdの担当環境ルール（STEP1は初回Windows環境、STEP2以降からの
  手戻り時のみLinux環境で可）に従って着手可否を判断している:
  - このチケットのSTEP1が未実施（初回）かつ現在のセッションがLinux環境の場合: STEP0相当の相談を
    Linux環境で受けた場合と同様に、Windows環境のセッションで同じチケット参照トリガーを使って
    STEP1を実施するようユーザーに提案する（本環境ではSTEP1に着手しない）
  - 現在のセッションがWindows環境の場合、またはLinux環境での手戻り（`00-REQUIREMENTS.md`の遡り
    修正）に該当する場合: そのままSTEP1に着手してよい
  - 実際にSTEP1に着手する時点（上記いずれの環境であっても）で、`update_issue_status.sh <id> 対応中`
    によりステータスを更新する
- **STEPが前後した場合**: 実装対象のチケットが分かっている場合、STEPが変わるたびに `add_issue_note.sh`
  でコメントを追記する。ステータスの変更は行わない。コメントの内容はSTEPが進む場合と戻る場合で異なる:
  - **STEPが進む場合**（例: STEP3完了→STEP4着手）: そのSTEPで実施した内容の概要を記録する
    （例: 「STEP3完了: ○○のテストケースを実装し、レッドを確認」）
  - **STEPが戻る場合**（例: STEP4からSTEP2に戻る）: なぜ前のSTEPに戻る必要が生じたのか、その理由を
    記録する（例: 「STEP4の実装中に設計の不整合が見つかったため、STEP2に戻って設計を見直す」）
- **設計判断を記録する場合**: チケットに紐づく作業中に重要な判断（仕様変更・スコープ決定・技術選定・
  命名決定など）が発生した場合は、判断内容をチャットで提示してユーザーの承認を得たうえで、CLAUDE.mdの
  「仕様変更・設計判断の記録」の詳細フォーマット（トリガー／背景・目的／決定事項／影響範囲）で
  `add_issue_note.sh` によりチケットへコメントとして記録する。`design_log.md`には判断の詳細を転記せず、
  STEPの節目に索引フォーマットで「どのチケットをどこまで進めたか」のみを記録する
- **実装完了時**: STEP6（ドキュメント反映）についてユーザーの承認を得たら、`update_issue_status.sh
  <id> 対応完了 <note_file>` でステータスを更新する。`design_log.md`への「完了」の索引は、
  プルリクエストのマージ後に追記しようとすると記録のためだけに別ブランチ・プルリクエストが必要になる
  ため、作業ブランチの最終コミット（プッシュ・プルリクエスト作成の前）に含めておく
- **子チケットを完了する場合（親チケットの完了）**: 親チケットの完了を記録するためだけに別ブランチ・
  プルリクエストを作らない。完了しようとしている子チケットが、親チケット配下で最後に残った未完了の
  子チケットである場合は、その子チケットの完了と同時に親チケットも完了とする:
  - `design_log.md`: 子チケットの「完了」の索引に `- **親チケット**: #<親チケットID> も本チケットの
    完了をもって完了（全子チケット完了）` の行を加え、上記「実装完了時」と同じく作業ブランチの最終
    コミットに含める。親チケット単独の索引エントリは作らない
  - Redmine: 子チケットを「対応完了」に更新した後、親チケットにも全子チケットが完了した旨のコメントを
    添えて `update_issue_status.sh <親チケットID> 対応完了` でステータスを更新する
  - 最後の子チケットでない場合は、親チケットのステータス・`design_log.md`とも変更しない
- **作業中に無関係な課題を発見した場合**: STEP0〜STEP6のいずれの作業中であっても、現在対応中の
  チケットと直接関係のない課題を発見した場合は、現在の作業スコープに含めず、新規チケットとして
  個別に登録する（親子構成はSTEP0で1つのテーマを分割する場合に限る）
- **ユーザー対応タスクの登録**: STEP0（壁打ち）の検討中など、AIではなくユーザー自身が対応する必要が
  あるタスクに気づいた場合、本スキルの「ユーザー対応タスクの登録」機能を使う。このチケットは開発
  フロー（STEP）に連動しないため、STEPが進む・戻るたびのコメント追記、`design_log.md`への索引記録、
  ステータス更新は行わない
